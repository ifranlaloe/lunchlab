LunchLab #2

Zooming with C4

Strong architecture conversations start by agreeing on zoom level: context first, details later.

Why this session

  • Align faster by naming the C4 level explicitly.
  • Avoid over-zooming too early in architecture discussions.
  • Use one shared language for scope and detail depth.

What you will get

  • A practical Level 1 + Level 2 facilitation workflow.
  • Case-based examples to separate context from implementation.
  • Facilitation prompts to keep scope under control.
C4 framing

C4 for traveler-system mapping

Core message

  • Architecture diagrams are maps.
  • Good maps are designed for a purpose.
  • Different traveler questions need different maps.
  • A useful map is not complete; it is purposeful.
  • C4 helps us choose the right traveler-system map before discussing design decisions.

Facilitation intent

  • Agree on map scale before discussing solution details.
  • Keep today mostly at Level 1 and Level 2.
  • Use Level 3 and Level 4 as references, not the main exercise scope.
Cheat sheet

C4 levels overview

Level 1 — System Context

Traveler-system map: The Netherlands in traveler context.
Question: What surrounds and connects to our system?

Level 2 — Container

Traveler-system map: Main traveler domains inside the system.
Question: What are the major traveler domains inside the system, and how do they connect?

Level 3 — Component

Traveler-system map: Inside one traveler domain.
Question: How is one major part structured internally?

Level 4 — Code

Traveler-system map: Implementation blueprint / specification.
Question: How is it built in exact detail?

WhatsApp case: C4 context at Level 1 and Level 2

L1

  • Actors: sender and receiver users.
  • Boundary: WhatsApp messaging platform.
  • External systems: APNs/FCM, SMS/OTP provider, device contacts.
  • Main interaction: secure chat/media exchange with offline push delivery.

L2

  • Clients: mobile/web/desktop apps with local message state.
  • Realtime edge: API gateway and persistent connection handling.
  • Core services: identity/auth + key management, messaging/fan-out, presence/receipts.
  • Platform services: media service, notification service, and data stores/queues/cache.

L3

  • Chat server internals: connection map, participant lookup, fan-out, ack handling.
  • Durable delivery flow: write message + per-recipient inbox before realtime publish.
  • Offline recovery: inbox lookup, message fetch, replay on reconnect, delete on ack.
  • Media path: attachment upload via separate HTTP/media service, then message reference.
  • Scale/failure controls: Redis pub/sub routing, heartbeats, sequence checks, retry polling.

L4

  • Command contracts: createChat, sendMessage, createAttachment, modifyChatParticipants, newMessage, chatUpdate, RECEIVED ack.
  • Data model details: Chat, ChatParticipant (+ participantId↔chatId GSI), Message, Inbox (TTL), Clients tables.
  • Connection details: WebSocket over TLS via L4 load balancer; user-level channel subscription.
  • Ordering behavior: server timestamps (NTP-synced) drive UI ordering, not strict causal order.
  • Implementation limits: group size 100, offline retention 30 days, bounded client count per account.
New case

Flink case: goal and requirements

Goal

Design a system where customers can quickly see what is deliverable from nearby distribution centers and place multi-item orders without double-booking physical inventory.

Functional requirements

  • Customers can query item availability by location for delivery within 1 hour.
  • Availability reflects the union of inventory across nearby DCs.
  • Customers can place one order containing multiple items.

Non-functional requirements

  • Availability lookups should be fast (<100ms).
  • Ordering must be strongly consistent to prevent double booking.
  • Scale target: up to 10k DCs and 100k catalog items.
  • Order throughput target: ~10 million orders/day.
Facilitation

Scope-control lines for the workshop

  • “Before deciding, let’s agree on the C4 level we are discussing.”
  • “Are we discussing system context, containers, components, or implementation detail?”
  • “That sounds like a Level 3 concern; let’s park it until we intentionally zoom in.”
  • “Let’s finish boundaries and responsibilities first, then discuss detailed design choices.”
  • “This belongs at implementation level; first align on the container interactions.”
  • “If we are debating framework or protocol specifics, we may be zoomed in too far.”
  • “Can we restate this decision in terms of latency, consistency, and ownership boundaries?”
Takeaway

Final takeaway

Start with C4 zoom-level alignment. Most workshop decisions should stay at Level 1 and Level 2 before moving into implementation detail.
